WhatsApp MCP

Dois processos locais que colocam a sua conta pessoal de WhatsApp atrás do Model Context Protocol. Um bridge em Go mantém a sessão multidevice viva e materializa o histórico em SQLite; um servidor MCP em Python lê esse SQLite direto e delega envios ao bridge por HTTP em localhost. Nada trafega para fora da máquina — exceto o que o agente decide ler.

Fluxos de execução

Quatro caminhos distintos. Repare que só um deles nasce no agente e chega ao WhatsApp — os outros três param antes.

Leitura

list_messages · list_chats · search_contacts · +5

  1. O agente chama a tool por stdio; FastMCP valida os argumentos.
  2. whatsapp.py abre uma conexão sqlite3 nova e monta o SQL com filtros de data, remetente, chat e texto.
  3. Com include_context=True, cada linha do resultado dispara uma consulta extra de vizinhança.
  4. As linhas viram dataclasses, _serializable() as achata em JSON e o agente recebe a resposta. O bridge não é acionado.

Envio

send_message · send_file · send_audio_message

  1. O agente informa recipient (telefone com DDI ou JID) e o conteúdo.
  2. Para áudio não-.ogg, audio.py chama o ffmpeg e grava um temporário Opus.
  3. POST localhost:8080/api/send com {recipient, message, media_path}.
  4. O bridge resolve o JID, faz upload da mídia com client.Upload() e monta o waProto.Message do tipo certo por extensão.
  5. Envio pelo whatsmeow; o eco volta como events.Message e é persistido como qualquer outra mensagem.

Download de mídia

download_media

  1. O agente passa message_id + chat_jid, ambos impressos junto das mensagens com mídia.
  2. POST /api/download; o bridge lê de messages a URL, a media_key e os dois SHA-256.
  3. Se o arquivo já existe em store/<chat-jid>/, retorna o caminho sem tocar na rede.
  4. Caso contrário, baixa e decripta via MediaDownloader e grava em disco.
  5. Volta o caminho absoluto — os bytes nunca entram no contexto do modelo.

Ingestão

contínua, independente do agente

  1. O bridge registra um handler único para Message, HistorySync, Connected e LoggedOut.
  2. Cada mensagem tem texto e metadados de mídia extraídos; sem nenhum dos dois, é descartada.
  3. StoreChat() atualiza last_message_time e StoreMessage() faz upsert por (id, chat_jid).
  4. O history sync inicial popula o retroativo — pode levar minutos após o pareamento.

Operação

O que precisa estar de pé e o que quebra na prática.

AspectoComportamento
BootOs dois processos sobem separados: go run main.go no bridge e o agente iniciando uv run main.py via stdio. As tools de leitura funcionam com o bridge parado — só ficam com dados congelados.
PareamentoQR code half-block no terminal, com timeout de 3 minutos. A sessão persiste em whatsapp.db; reautenticação a cada ~20 dias.
ResyncNão há reconciliação incremental. Fora de sincronia, o procedimento é apagar messages.db e whatsapp.db e parear de novo.
Windowsgo-sqlite3 usa cgo: exige CGO_ENABLED=1 e um compilador C instalado.
ConfiguraçãoNenhuma. Porta, caminhos de banco e URL base são constantes no código, dos dois lados.
TestesUm arquivo, tests/test_mcp_structured_results.py, cobrindo a serialização de dataclasses com a camada whatsapp mockada.

Arestas arquiteturais

Achados da leitura do código, ordenados por consequência. Nenhum é bloqueante para uso pessoal; todos são bloqueantes para uso multiusuário.

Exposição

A API REST não tem autenticação e escuta em todas as interfaces. startRESTServer monta o endereço como ":8080", não "127.0.0.1:8080". Qualquer processo local — e qualquer host da mesma rede, num Wi-Fi aberto — pode chamar /api/send e mandar mensagens como você. Correção de uma linha.

Exfiltração

send_file aceita um caminho absoluto arbitrário vindo do modelo e o bridge o lê com os.ReadFile sem nenhuma restrição de diretório. Combinado com leitura de mensagens (conteúdo não confiável) e envio para fora, é exatamente a lethal trifecta que o README sinaliza. Um allowlist de diretórios fecharia o caso.

Contrato

A tool list_messages não devolve o que sua assinatura promete. whatsapp.py::list_messages é anotada -> List[Message] mas retorna a string de format_messages_list(); _serializable() repassa strings intactas, então o agente recebe texto formatado onde o schema MCP declara List[Dict]. O mesmo vale para get_last_interaction. O teste existente não pega isso porque mocka a camada inteira.

Desempenho

N+1 no caminho mais usado. Com include_context=True (padrão), cada mensagem retornada dispara um get_message_context — que abre uma conexão SQLite nova e roda três queries. Um limit=20 vira 61 queries e 21 conexões. Uma window function resolveria em uma.

Correção

Dois joins e um filtro frágeis. list_chats e get_chat ligam a última mensagem por igualdade de timestamp (chats.last_message_time = messages.timestamp), o que duplica a linha quando duas mensagens colidem no mesmo instante; get_direct_chat_by_contact casa com LIKE %numero%, que pode acertar o contato errado quando um número é substring de outro.

Evolução

Sem migrations. O schema nasce de CREATE TABLE IF NOT EXISTS; qualquer coluna nova exige apagar o banco e refazer o history sync. É a razão pela qual o troubleshooting do README trata "apagar os dois .db" como procedimento padrão.
